# 楽楽精算の「できること／できないこと」とAI活用による収支把握の設計案

作成日: 2026-09-02

> 前提: ご依頼の「らくらくせいさん」は、株式会社ラクスの経費精算システム **楽楽精算** を指すものとして整理しています。
> （個人事業主向けの「らくらく青色申告」等の別製品であった場合、下記のギャップの一部は変わります。要確認）

---

## 0. 結論（先に要点）

- 楽楽精算は **「支出の申請 → 承認 → 仕訳出力」に特化した業務システム** であり、経営管理のためのBI/分析ツールではない。
- 「収支の把握が難しい」のは運用の問題ではなく **構造上の問題**。収支 = 売上 − 費用 のうち、楽楽精算には **売上（収入）が存在しない**。さらに費用も「経費精算を通った分」だけで、人件費・原価・減価償却などは含まれない。
- したがって解決策は「楽楽精算の使い方を工夫する」ではなく、**楽楽精算・会計ソフト・売上データ・銀行口座を1か所に集約し、その上にダッシュボードとAIを載せる** こと。
- AIの役割は **集計ではなく、統合・説明・検知・予測**。数値の計算はSQL（監査可能）に任せ、AIは「なぜそうなったか」「どこがおかしいか」「この先どうなるか」を担当させるのが安全かつ効果的。

---

## 1. 楽楽精算でできること

| 領域 | できること |
|---|---|
| 交通費精算 | 交通系ICカードの読取取込、乗換案内連携による運賃自動計算、定期区間の自動控除 |
| 経費精算 | 領収書のスマホ撮影＋OCR自動読取、立替・仮払・外貨精算 |
| ワークフロー | 部門別・金額別の多段承認、差戻し、代理承認、申請フォームと承認経路のカスタマイズ |
| 規程チェック | 上限額オーバーや必須項目未入力などの **静的ルール** による自動チェック |
| カード連携 | 法人カード利用明細の自動取込 |
| 請求書・支払 | 受取請求書の登録／支払依頼、支払管理、全銀（FB）データの自動作成 |
| 法対応 | インボイス制度（登録番号チェック）、電子帳簿保存法（タイムスタンプ・検索要件・証憑の電子保存） |
| 会計連携 | 勘定科目・税区分の自動仕訳、会計ソフト別フォーマットでの仕訳CSV出力 |
| 集計・出力 | 伝票データ出力（プロジェクト別・負担部門別など分析用CSV） |
| 予算管理 ※オプション | 部門別・プロジェクト別の**経費**予算設定、超過時のアラート／申請ブロック、予実対比（予算・実績・申請・精算・予実差・消化率） |
| API連携 ※オプション | 仕訳データ出力API、各種マスタへのCSV自動取込 |
| モバイル | スマホアプリからの申請・承認 |

**要点**: 「経費という支出を、正しく・早く・法令準拠で処理して会計へ渡す」までは非常に強い。

## 2. できないこと（＝収支が見えない理由）

各ギャップに **G番号** を付与。第3章のAIソリューションはこの番号を参照する。

| ID | できないこと | なぜ困るか |
|---|---|---|
| **G1** | **収入（売上・入金）を一切扱わない** | 収支の片側しか無い。楽楽精算だけを見ても収支は原理的に出ない |
| **G2** | 会計帳簿そのものではない（総勘定元帳・試算表・PL/BS・部門別損益は会計ソフト側） | 費用も「経費精算を通った分」のみ。人件費・仕入原価・減価償却・地代家賃などが欠落し、実際のコスト構造が分からない |
| **G3** | 数字が「申請ベース」でしか動かない | 未申請の経費は存在しないことになる。月末にまとめて申請されるため、月中の着地見込みが読めない |
| **G4** | 予算管理は**経費予算のみ**、かつオプション | 売上予算・人件費予算・外注費と分断され、「部門の予実」が全体では組めない |
| **G5** | 分析の切り口が固定 | 「なぜ増えたのか」「どの案件・誰・どの取引先か」の深掘りは、結局CSV出力→Excelの手作業になる |
| **G6** | 複数システム横断のビューが無い | 会計ソフト／販売管理・請求／銀行口座／給与 と分断。誰かが毎月Excelで手で束ねている |
| **G7** | 予測・資金繰りができない | 出るのは過去実績の集計のみ。来月の着地見込みや資金ショートの予兆は出ない |
| **G8** | 異常検知が静的ルールのみ | 上限額チェックは可能だが、二重申請・相場から外れた金額・特定取引先への急増などは人が目視するしかない |
| **G9** | 数字は出るが「説明」は出ない | 月次報告のコメントは毎回人が書いている |
| **G10** | 現場が自分の数字を見に行きにくい | ライセンス・権限の制約もあり、経理が聞かれるたびに抽出して返す運用になりがち |

## 3. AIを使ったアプリ／ダッシュボードでの解決案

### 3.1 全体構成（3層）

```
[ Layer 1  データ統合 ]
  楽楽精算（伝票/仕訳データ）
  会計ソフト（試算表・総勘定元帳）
  販売管理・請求システム（売上・入金）      ──►  データ基盤（DWH）
  銀行/カード明細（実キャッシュ）                日次バッチで集約・正規化
  給与/勤怠（人件費・工数）
        │
        │  AI: 取引先名の名寄せ、科目マッピング推定、部門・案件コードの補完
        ▼
[ Layer 2  ダッシュボード ]  ← 数値の計算はすべてSQL（監査可能）
        │
        ▼
[ Layer 3  AI インテリジェンス ]
  自然言語Q&A / 異常検知 / 月次サマリー自動生成 / 着地・資金繰り予測
```

### 3.2 設計原則（最重要）

> **「数字はSQL、言葉はAI」**

LLMに集計させない。表示されるすべての数値は監査可能なクエリの結果とし、AIは
①クエリを書く ②結果を日本語で説明する ③異常を指摘する ④将来を予測する、に限定する。
これでAIの数値ハルシネーションによる経営判断ミスを構造的に防げる。すべての数値に「元の伝票を見る」リンクを付ける。

### 3.3 ダッシュボード画面案

| 画面 | 内容 | 解消するギャップ |
|---|---|---|
| 全社サマリー | 売上／費用／営業利益／現預金残高、前年同月比・予算比 | G1, G2, G6 |
| 部門別・案件別損益 | 売上と人件費を配賦した「本当の採算」。経費だけの採算から脱却 | G2, G4 |
| 予実＆着地見込み | 未申請・未計上分の見込みを加えた月末着地予測 | G3, G4, G7 |
| コスト内訳ドリルダウン | 科目 → 部門 → 取引先 → 伝票 まで1クリックで降りられる | G5 |
| 資金繰り12週予測 | 入金予定・支払予定・実績から週次のキャッシュ推移 | G7 |
| 要確認リスト | AI異常検知の結果を「承認前に潰すべき順」で提示 | G8 |
| 現場向けビュー | 部門長は自部門のみ、案件責任者は自案件のみ。権限で出し分け | G10 |

### 3.4 AIが担う具体機能

1. **自然言語Q&A**（G5, G9, G10）
   「今月の交際費が前年より多いのはなぜ？」→ SQL生成 → 要因分解（部門・取引先・件数×単価）→ 該当伝票へのリンク付きで回答。経理への問い合わせ工数がそのまま消える。
2. **月次サマリーの自動生成**（G9）
   主要な変動要因を3〜5行に要約し、毎朝／月次でSlack・メールへ自動配信。
3. **異常検知**（G8）
   二重申請、金額の外れ値、規程の実質的な逸脱、特定取引先への急増、曜日・季節性を踏まえた異常。静的ルールでは書けない検知をモデルが担当。
4. **着地・資金繰り予測**（G3, G7）
   過去の申請タイミングの癖を学習し「未申請だがまだ出てくるはずの経費」を推定して着地に織り込む。
5. **勘定科目・部門コードの推定精度向上**（G2）
   過去の確定仕訳を学習して推定。結果を楽楽精算のマスタへ書き戻せば、入力段階の品質そのものが上がる。
6. **証憑の読取と突合**（G8）
   領収書・請求書PDFを読み取り、申請内容・発注・支払予定との三点照合。

## 4. データ連携の現実的な選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| **A. 会計ソフト側を正とする** | 楽楽精算 → 会計ソフト の連携は既に稼働しているはず。分析基盤は**会計ソフトのAPI**から取得する | **推奨の起点**。二重取得を避けられ、費用も工数も最小。人件費・原価も一緒に取れる |
| B. 楽楽精算のAPI連携オプション | 仕訳データ出力API、マスタCSV自動取込。※「伝票データ出力」はAPI非対応との記載あり（要確認） | 経費の明細粒度が必要な場合に追加。オプション契約と開発が必要 |
| C. 定期CSV出力＋自動取込 | 管理画面から出力 → 共有フォルダ → ETL。iPaaS（ActRecipe / CData Arc / Yoom 等）に既製レシピあり | 最短で動く。まずここから始めて後でAに寄せるのも可 |

## 5. 進め方（フェーズ）

| Phase | 期間目安 | やること | 成果物 |
|---|---|---|---|
| 0 | 1〜2週 | 現状棚卸し。**今Excelで作っている資料を全部集める**（＝要件定義そのもの）。「収支」の定義を合意（全社PL／部門別／案件別／キャッシュ、どれか） | KPI定義書 |
| 1 | 2〜4週 | データ連携＋最小ダッシュボード。まず「全社PL＋部門別＋予実」の1画面だけ作り切る | 動くダッシュボード |
| 2 | 1〜2ヶ月 | AI機能追加：自然言語Q&A、異常検知、月次サマリー自動配信 | AIアシスタント |
| 3 | 以降 | 着地・資金繰り予測、楽楽精算への書き戻し自動化 | 予測・自動化 |

Phase 1を欲張らないことが成否を分ける。1画面が毎朝見られる状態になってから広げる。

## 6. 注意点・リスク

- **電子帳簿保存法**: 証憑の原本は楽楽精算側に置いたままにし、分析基盤にはメタデータのみを持つ。証憑のコピーを持つ場合は保存要件を満たす場所に置く。
- **個人情報・機微情報**: 個人別の経費データは実質的に人事情報。閲覧権限を「部門長は自部門のみ」等に厳密に分ける。LLMに渡す前に個人名等をマスキングし、学習利用オフの契約形態を選ぶ。
- **AIの数値誤り**: 3.2の設計原則（数字はSQL、言葉はAI）で構造的に回避する。
- **オプション費用**: 楽楽精算の予算管理・API連携はオプションで、料金は公開されていない。**既存の楽楽精算オプションだけで要件が満たせるならそれが最安**なので、内製する前に必ず見積・機能確認を行う。
