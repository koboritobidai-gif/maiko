# 情報管理の再設計（Slack / スプレッドシート / Lステップ）

作成日: 2026-08-18

## 0. 結論（先に3行）

1. **一次情報の置き場所を「3枚のシート」に固定する**。求職者・企業求人・選考進捗の3枚だけがマスタで、それ以外は全部「ビュー」か「アーカイブ」に格下げする。
2. **Slack は情報の保管場所をやめて、入口（入力フォーム）と出口（通知）にする**。報告する行為とデータ入力する行為を同じ1操作にまとめれば、入力工数は増えない（むしろ減る）。
3. **漏れは人の記憶ではなくシステムで検知する**。全レコードに「次アクション」「期限」「担当」を持たせ、期限超過を毎朝 Slack に自動でメンション投稿する。

---

## 1. いま何が起きているか（問題の構造化）

ツールが3つあることが問題なのではなく、**同じ情報が3箇所に書けてしまうこと**が問題です。

| 現象 | 本当の原因 |
|---|---|
| 情報が散らばる | 「この情報はここに書く」という所有者（マスタ）が決まっていない |
| 漏れが多い | 報告（Slack）と記録（シート）が別作業なので、片方だけやって終わる |
| 必ずある場所がない | Slack が事実上の保管場所になっているが、Slack は流れる媒体で検索も一覧も弱い |
| シートが複数ある | 必要になるたびに新しいシートを作り、統廃合していない |

したがって打ち手は「ツールを減らす」ではなく、**役割を1つずつに限定して、転記を自動化する**ことです。

---

## 2. 基本方針（3原則）

### 原則1: 1つの情報の一次ソースは必ず1箇所

- 求職者のことを知りたい → **求職者マスタ**
- 企業・求人のことを知りたい → **企業求人マスタ**
- いま選考がどうなっているか → **選考進捗**
- 経緯・議論・判断 → Slack（ただし必ず求職者ID付きで紐づける）

「Slack を探す」から「シートを見る、詳しい経緯だけ Slack を辿る」に変える。

### 原則2: 同じ情報を人が2回入力しない

現状はおそらく「面談 → Slack に報告文を書く → 別途シートに転記」。
これを「**Slack のフォームに入力 → シートに自動追記 + 整形済みメッセージが自動投稿**」に変える。
人の操作は1回。しかも項目が決まっているので、報告文を考える手間がなくなる。

### 原則3: 漏れは仕組みで検知する

全レコードに「次アクション / 期限 / 担当」を必須で持たせ、期限超過を毎朝 Slack に自動通知。
「誰かが気づく」に依存しない。

---

## 3. 目指す構成

```
[Lステップ]  ← 求職者との接点（LINE）・アンケート回収・自動応答
     │ 自動連携（API または定期エクスポート）
     ▼
[Googleスプレッドシート（マスタ3枚）]  ← ★ここに必ず情報がある
     │  ┌ 求職者マスタ
     │  ├ 企業求人マスタ
     │  └ 選考進捗
     ▲                     │
     │ Slackワークフローで入力  │ GASで自動通知
     │                     ▼
[Slack]  ← 入力の入口 / 通知の出口 / 議論の場（保管場所ではない）
```

各ツールの役割を1行で定義：

- **Lステップ**: 求職者との連絡手段と、初期情報の自動収集装置。管理台帳としては使わない。
- **スプレッドシート**: 唯一の台帳（マスタ）。
- **Slack**: 入力インターフェースと通知チャンネル。ここに一次情報を書かない。

## 4. マスタ3枚の設計

### 4-1. 求職者マスタ（1行 = 1求職者）

| 列 | 内容 | 入力元 |
|---|---|---|
| 求職者ID | `C-0001` 形式で自動採番。**全システム共通のキー** | 自動 |
| LINE友だちID / 表示名 | Lステップとの名寄せキー | Lステップ連携 |
| 氏名 / フリガナ | | Lステップ アンケート |
| 電話 / メール | | Lステップ アンケート |
| 流入経路 | 媒体名・紹介元 | Lステップ流入元 |
| 登録日 | | 自動 |
| ステータス | 未接触 / 面談調整中 / 面談済 / 紹介中 / 選考中 / 内定 / 入社 / フォロー中 / 失注 | Slackフォーム |
| 担当CA | | Slackフォーム |
| 希望条件 | 職種・勤務地・希望年収・就業開始時期 | 面談報告フォーム |
| 経歴サマリ | 3行程度 | 面談報告フォーム |
| 最終接触日 | | 自動更新 |
| **次アクション** | 例「求人3件提案」 | Slackフォーム |
| **次アクション期限** | 日付 | Slackフォーム |
| Slackスレッドリンク | 詳細な経緯へのリンク | 自動 |

### 4-2. 企業求人マスタ（1行 = 1求人）

企業ID・求人IDを分け、1企業に複数求人がぶら下がる形にする。

| 列 | 内容 |
|---|---|
| 求人ID | `J-0001` |
| 企業ID / 企業名 | |
| 担当RA | |
| 求人タイトル / 職種 / 勤務地 | |
| 給与レンジ | |
| 必須要件 / 歓迎要件 | |
| 選考フロー | 書類→一次→最終 など |
| 手数料率 / 想定フィー | |
| 募集状況 | 募集中 / 一時停止 / クローズ |
| 最終確認日 / 次回確認期限 | ★求人の鮮度切れを防ぐ |

### 4-3. 選考進捗（1行 = 1エントリー = 求職者ID × 求人ID）

**ここが一番の肝**です。求職者マスタに選考状況を書くと、1人が複数社受けたときに破綻します。必ず別シートで交差させる。

| 列 | 内容 |
|---|---|
| エントリーID | `E-0001` |
| 求職者ID → 氏名 | VLOOKUPで自動表示 |
| 求人ID → 企業名 | VLOOKUPで自動表示 |
| 推薦日 | |
| ステータス | 推薦 / 書類選考中 / 書類通過 / 一次 / 二次 / 最終 / 内定 / 承諾 / 入社 / 辞退 / NG |
| **次アクション / 期限 / 担当** | ★漏れ検知の対象 |
| 結果理由 | NG・辞退の理由（後で分析に効く） |
| 想定売上 / 入社予定日 / 請求日 | 売上見込みの管理 |

この3枚だけで、「今月の売上見込み」「動いていない求職者」「止まっている選考」が全部 QUERY 関数で出せます。

## 5. 入力工数を増やさない仕掛け（ここが本題）

### 5-1. Slack ワークフローを「入力フォーム」にする

Slack のワークフロービルダーでフォームを作り、送信すると
**(a) スプレッドシートに行が追加され、(b) 整形されたメッセージがチャンネルに投稿される**ようにします。

作るフォームは最初は3つだけ：

| フォーム | 起動場所 | 入力項目 | 書き込み先 |
|---|---|---|---|
| 面談完了報告 | `#報告-面談` | 求職者ID、面談日、希望条件、経歴サマリ、次アクション、期限 | 求職者マスタを更新 |
| 推薦・選考更新 | `#進捗-選考` | 求職者ID、求人ID、新ステータス、次アクション、期限 | 選考進捗に追記 |
| 企業ヒアリング報告 | `#報告-企業` | 求人ID（新規なら企業名）、募集状況、変更点、次回確認日 | 企業求人マスタを更新 |

**工数の比較**：
- 現状: Slack に報告文を書く（文章を考える）＋ シートに転記 = 2作業
- 改善後: フォームの項目を埋める = 1作業（しかも選択式中心で文章を考えなくていい）

つまり**入力工数は増えず、むしろ減ります**。ここを守れないなら他は全部やらなくていいくらい重要です。

> 補足: Slack のワークフローから Google スプレッドシートへ書き込むステップは有料プランの機能です。無料プランの場合は「Google フォーム（スマホでも1画面）→ 回答がシートに入る → GAS が Slack に整形投稿」で全く同じ体験が作れます。どちらでも成立するので、プランに合わせて選べば OK。

### 5-2. Lステップ側は「入力しない」

友だち追加直後のアンケートで、氏名・連絡先・希望条件・経歴の基本項目を取得し、
その回答を求職者マスタへ自動で流し込みます。**CA の手入力はゼロ**。

- Lステップの外部連携／API が使えるプランなら、リアルタイムで連携。
- 使えないプランなら、回答データを週1でエクスポートし GAS で取り込む（作業5分）。
  それでも「手で転記」よりは圧倒的に速く、漏れません。

名寄せのキーは **LINE友だちID**。LINE の表示名は本名と違うことが多いので、表示名をキーにしない。

### 5-3. 出力（報告）も自動化する

シートのステータス列が変わったら、GAS が Slack に自動投稿します。

```
🟢 選考ステータス更新
求職者: 山田太郎（C-0042）
企業: 株式会社◯◯ / 営業（J-0015）
書類選考中 → 書類通過
次アクション: 一次面接の日程調整（担当: 佐藤 / 期限 8/22）
▶ シートで見る: <リンク>
```

これで「報告のために Slack に書く」作業自体がなくなります。

## 6. 漏れを検知する仕組み

GAS のトリガーで自動実行。**これが「漏れが多い」への直接の回答**です。

| 頻度 | 内容 | 投稿先 |
|---|---|---|
| 毎朝9時 | 次アクション期限が「今日 or 超過」のものを担当者ごとにまとめて投稿（@メンション付き） | `#todo-アラート` |
| 毎週月曜 | 最終接触日から14日以上経過し、かつ未クローズの求職者一覧 = 放置リスト | `#todo-アラート` |
| 毎週月曜 | 30日以上更新のない「募集中」求人 = 鮮度切れリスト | `#todo-アラート` |
| 随時 | 必須項目が空欄の行を条件付き書式で赤表示 | シート上 |

「気づいた人が拾う」から「システムが毎朝突きつける」に変わります。

## 7. Slack の運用ルール（4行だけ）

1. **一次情報を Slack 本文に書かない**。書いた瞬間にそれは失われる情報だと考える。
2. 求職者・求人の話をするときは**必ず ID を書く**（`C-0042` `J-0015`）。自動投稿には常に ID が入るので、Slack 検索が索引として機能する。
3. チャンネルは目的で分ける：`#報告-面談` `#報告-企業` `#進捗-選考`（自動投稿専用、雑談禁止）、`#相談`（人間の議論）、`#todo-アラート`（自動リマインド）。
4. 議論は必ず**スレッドで**。親メッセージに ID があれば経緯が全部そこに紐づく。

## 8. 既存スプレッドシートの棚卸し手順

「複数ある」問題は、統合より先に**棚卸し**をやらないと必ずまた増えます。

1. **一覧化**: 今あるシートを全部リストアップ（名前 / 作った人 / 何のため / 最終更新日 / 現在使っているか）。
2. **分類**: それぞれを ①マスタ候補 ②集計・分析用 ③もう使っていない、の3つに仕分ける。
3. **列の突合**: ①のシートの列を全部書き出し、重複・呼び方違い（「希望年収」と「年収希望」など）を統一する。
4. **統合**: 上記の3枚に集約。
5. **旧シートを凍結**: 削除せず、ファイル名の先頭に `【凍結】` を付け、**全員を閲覧専用**にして1行目に「このシートは使用終了。最新は◯◯」と赤字で明記。削除すると不安で新シートを作る人が出るので、消さずに凍結が正解。
6. **新規作成のルール化**: 新しいシートを作りたくなったら、まず「3枚のマスタに列を足せないか」を検討する。作る場合も**マスタを参照するビュー（QUERY / IMPORTRANGE）**にして、データを二重に持たない。

## 9. 導入ステップ

| 時期 | やること | 効果 |
|---|---|---|
| **Week 1** | シートの棚卸し（手順8の1〜3）。マスタ3枚の列を確定。求職者IDの採番ルールを決める | 現状把握、認識合わせ |
| **Week 2** | マスタ3枚を作成し、既存データを移行。旧シートを凍結 | 「必ずここにある」場所が誕生 |
| **Week 3** | Slack ワークフロー3種を作成 → 報告＝入力を一本化。Slack 運用ルールを周知 | 二重入力の解消 |
| **Week 4** | GAS で毎朝のアラートと自動投稿を実装 | 漏れの構造的検知 |
| **Month 2** | Lステップ連携（API or 定期取込）。数字の集計ダッシュボードを1枚追加 | 手入力ゼロ化、経営数値の可視化 |

最初の2週間で「必ずここにある場所」ができ、3週目で工数が下がります。**この順番を崩さない**こと（先に自動化に手を付けると、統合されていないシートを自動化してしまい二度手間になります）。

## 10. 将来の選択肢（今は不要、判断基準だけ持っておく）

スプレッドシート運用は安く速い一方、件数と人数が増えると限界が来ます。以下のどれかに当てはまったら専用ツールを検討：

- 同時に動く選考エントリーが常時 50件を超える
- シートを編集するメンバーが 5〜6名を超える（同時編集で事故る）
- 誰がいつ何を変えたかの履歴を追う必要が出た
- 求職者ごとの書類・職務経歴書の管理が煩雑になった

候補と性格：

| ツール | 向き | 補足 |
|---|---|---|
| 採用管理システム（ATS / 人材紹介向け） | 本命 | 人材紹介の業務にそのまま乗る。移行コストは高い |
| kintone | 中間 | 自社の項目に合わせて作れる。Slack 連携も容易 |
| Notion / Airtable | 軽量 | 見やすいが、件数が増えると重くなる・集計が弱い |

**重要**: ツールを変えても、本ドキュメントの原則1〜3（一次ソースを1つに / 二重入力しない / 漏れを機械が検知する）が守られていなければ同じ問題が再発します。逆に原則さえ守れば、スプレッドシートのままでも十分回ります。

## 11. 確認が必要な前提

実装方法がここで分岐するので、着手前に確認してください。

1. **Slack のプラン**: 有料ならワークフローから直接シートに書き込めます。無料なら Google フォーム + GAS 構成に切り替えます（体験はほぼ同じ）。
2. **Lステップのプラン**: 外部連携／API が使えるかで、リアルタイム連携か定期取込かが決まります。
3. **規模感**: 月間の新規求職者数、同時進行の選考件数、シートを触るメンバー数。3枚構成で足りるか、最初からツール導入を検討すべきかの判断材料になります。
4. **Google Workspace の利用有無**: GAS とシートの権限管理（保護範囲・編集権限）の設計に影響します。
