# 情報管理の再設計（Slack / スプレッドシート / Lステップ）

作成日: 2026-08-18 / 実データ調査反映版

## 0. 結論（先に4行）

1. **1つのファイルにまとめるのは不可能だし、やるべきでもない**。求職者リストが分かれているのは「送客元パートナーごとの共有シート」だからで、相手が入力する以上そこは統合できない。
2. ゴールは物理的な1ファイルではなく、**論理的に1つの場所**。入力元は今のまま一切触らず、**読み取り側だけを1本に集約**する（＝IMPORTRANGE / GASで吸い上げる）。相手の運用も自社の入力工数も変わらない。
3. 編集していいシートを**3枚だけ**に絞る（求職者マスタ / 求人マスタ / 選考進捗）。残りは全部「自動生成のビュー」に格下げして読み取り専用にする。**ビューは何枚あってもいい。**
4. いま最大の欠落は **「選考進捗」の明細が存在しないこと**。集計値を手入力しているため、漏れが検知できず、集計作業自体が工数になっている。ここを作ると入力工数は**純減**する。

### 1-3. 決定的な問題：集計を手入力している

`★面談・面接管理シート` の中身を確認したところ、シート内に以下の注記がありました。

- 「**【手入力：面接実施数・面接日程確定数（月次）】**」
- 「※青い部分は手入力」「※黄色い部分は毎月手動更新」
- 「←毎月手動更新」「※担当CAの列に数字を入れる」
- タブ名が「**面接数6月 のコピー**」＝毎月タブを複製している

つまり **面談数・面接数・内定数・採用決定数を、CAごとに人間が数えて打ち込んでいる**。
明細（1行 = 1面談 / 1選考）が存在しないため、

- 数字の根拠を後から追えない
- 「まだ動いていない求職者」を機械的に洗い出せない → **これが漏れの直接原因**
- 毎月の集計作業そのものが工数になっている
- 月次でタブを複製するのでファイルが肥大化（38.6MB）

### 1-4. 求人マトリックスは「セル＝1求人カード」で、色に意味を持たせている

`求人マトリックス（改善版Ver2.0）` は `【東京】営業` のようなタブに、B4・C4・D4 …と**1セルに求人1件を全文テキストで**入れる形式でした。さらに「休日区分水色 / 緑色 / 黄色 / 橙色」「検索除外」といった**色に意味を持たせた運用**があります。

一方 `送客可能企業リスト(prod)` は `企業名 / 状態 / 勤務地 / 業界 / 職種 / 経験 / 年齢 / 下限固定年収 / 休日 / 外国人受入 / 検索タグ / 求人票 / 議事録リンク` という正しい表形式です。

**同じ求人情報が「表」と「カード＋色」という互換性のない2つの形で、別々の人によって手動更新されている。** だから乖離するし、統合が難しく感じられます。

なお `送客可能企業リスト(prod)` にも構造上の弱点があり、**1行＝1企業**になっています（例：エー・ファクトリー株式会社の「営業」と「事務」が1行に同居）。このままだと求人単位で選考を紐づけられません。

## 2. なぜ「1つにまとめる」のが難しいのか

理由は3つあり、**うち1つは正しい制約、2つは直せる問題**です。

| # | 理由 | 判定 | 対処 |
|---|---|---|---|
| A | 送客元パートナーごとに共有シートが分かれている | **正しい制約。統合不可** | まとめない。自動で吸い上げるだけ |
| B | 同じ情報が「表」と「カード＋色」で形が違う | 直せる | 片方を表示専用ビューに落とす |
| C | 明細がなく集計値しか持っていない | 直せる | 明細1枚を作れば集計は自動になる |

**Aがあるので「1ファイルにまとめる」は永遠に達成できません。** ここを目標にしている限り徒労が続きます。

## 3. 正しいゴール：3層に分ける

物理的に1ファイルにするのではなく、**「編集していい場所」を1つにする**。

```
【入力層】── 今のまま。一切変えない（＝入力工数ゼロ増）
  ・送客元パートナー各社の共有シート（KANOA / マホガニー / foresma / 人事パートナーズ / kthr37 …）
  ・Lステップ（自社流入・アンケート回収）
  ・Slackワークフロー（面談報告・選考更新）
        │
        │  IMPORTRANGE / GAS で自動吸い上げ（相手は何も変えなくていい）
        ▼
【統合層】── ★ここが「必ず情報がある場所」。編集していいのはここだけ
  ① 求職者マスタ    全ソースを縦積み＋名寄せ（自動）
  ② 求人マスタ      送客可能企業リスト(prod) を 1行=1求人 に割り直したもの
  ③ 選考進捗        1行 = 求職者 × 求人 ← ★今どこにも存在しない
        │
        │  QUERY / SUMIFS で自動生成
        ▼
【出力層】── 何枚あってもいい。全部読み取り専用。手入力しない
  ・求人マトリックス（表示ビュー）
  ・週次 / 月次KPI（自動集計）
  ・クライアント提出用リスト（会社ごとに自動出力）
  ・Slack自動通知・アラート
```

### 仕分けルール（これだけ覚えればいい）

> **そのシート、誰かが手で書き換えている？ → マスタ。見るだけ？ → ビュー。**
> **マスタを3枚に減らし、それ以外は全部ビューにして読み取り専用にする。**

いまは全ファイルが「編集可能なマスタ」になっているので、どこにでも書けてしまい、どこにも揃わない。**出力層のシートが何枚あっても混乱しません。混乱するのはマスタが複数あるときだけです。**

## 4. マスタ3枚の設計

### ① 求職者マスタ（1行 = 1求職者）

各パートナーシートを IMPORTRANGE で縦積みし、**列名の違いはマッピング表1枚で吸収**します（相手のシートは触らない）。

| 列 | 内容 |
|---|---|
| 求職者ID | `C-0001` 自動採番。全システム共通キー |
| 流入元 | パートナー名 / Lステップ / 媒体名 |
| 元シート行リンク | 一次情報へ戻れるように |
| 氏名 / フリガナ / 年齢 / 居住地 / 電話 / メール | |
| LINE友だちID | Lステップとの名寄せキー（表示名は本名と違うので使わない） |
| 課金形態 | 着座課金 / 成果報酬 など（パートナーごとに違う） |
| 担当CA | |
| ステータス | 未接触 / 面談調整中 / 面談済 / 紹介中 / 選考中 / 内定 / 入社 / 失注 |
| 希望条件 | 職種・勤務地・希望年収・入社可能時期 |
| **次アクション / 期限** | ★漏れ検知の対象 |
| 面談情報リンク | ★長文は本文に入れずリンクで持つ（後述のサイズ問題対策） |

### ② 求人マスタ（1行 = 1求人）

`送客可能企業リスト(prod)` をベースに、**1行1企業 → 1行1求人**へ割り直し、`J-0001` を採番。
マトリックスの「色」は列に落とします（`休日区分`、`掲載可否`＝旧「検索除外」）。

既存の列（状態 / 勤務地 / 業界 / 職種 / 営業スタイル / 経験 / 年齢 / 下限固定年収 / 休日 / 外国人受入 / 検索タグ / 求人票 / 議事録リンク）はそのまま活かせます。

### ③ 選考進捗（1行 = 1エントリー = 求職者ID × 求人ID）★新規

**これが今いちばん足りていないものです。**

| 列 | 内容 |
|---|---|
| エントリーID | `E-0001` |
| 求職者ID → 氏名 / 求人ID → 企業名 | VLOOKUPで自動表示 |
| 担当CA | |
| 推薦日 / 面談日 / 面接確定日 / 面接実施日 / 内定日 / 採用決定日 | ★日付を1行に持つ |
| ステータス | 推薦 / 書類選考中 / 一次 / 二次 / 最終 / 内定 / 承諾 / 入社 / 辞退 / NG |
| **次アクション / 期限** | |
| 結果理由 | NG・辞退の理由 |
| 想定売上 / 請求発生月 | |

この1枚があれば、`★面談・面接管理シート` の週次管理・月次タブは**すべて自動計算に置き換わります**。
「佐藤 / 竹林 / 別府 / 寺本 …」のCA別集計も `SUMIFS` 一発。**毎月の手入力と月次タブ複製がまるごと消えます。**

## 5. 入力工数を増やさない仕掛け

### 5-1. パートナー共有シートは触らない

相手に入力形式の変更をお願いすると必ず失敗します。**こちらが読み取る側で吸収**します。
IMPORTRANGE + マッピング表なので、相手の作業は今日と1ミリも変わりません。

### 5-2. Slackのフォームを入力インターフェースにする

Slackワークフローでフォーム送信 → ①シートに行追加、②整形済みメッセージがチャンネルに自動投稿。

| フォーム | 入力項目 | 書き込み先 |
|---|---|---|
| 面談完了報告 | 求職者ID、面談日、希望条件、次アクション、期限 | 求職者マスタ |
| 推薦・選考更新 | 求職者ID、求人ID、新ステータス、次アクション、期限 | 選考進捗 |
| 企業ヒアリング報告 | 求人ID、募集状況、変更点、次回確認日 | 求人マスタ |

- 現状：Slackに報告文を書く ＋ シートに転記 = 2作業
- 改善後：フォームを埋める = 1作業（選択式中心で文章を考えなくていい）

さらに月次集計の手入力が消えるので、**トータルでは明確に工数減**です。

> Slackワークフローからシートへの書き込みは有料プランの機能です。無料プランなら「Googleフォーム → 回答がシートに入る → GASがSlackに整形投稿」で同じ体験になります。

### 5-3. Lステップは入力せず、流し込む

友だち追加直後のアンケートで基本情報を取得し、求職者マスタへ自動反映。CAの手入力はゼロ。
API連携が使えないプランなら、週1のエクスポート取込（5分）で代替可能です。

## 6. 漏れを検知する仕組み

選考進捗ができて初めて成立します。GASのトリガーで自動実行。

| 頻度 | 内容 | 投稿先 |
|---|---|---|
| 毎朝9時 | 次アクション期限が今日 or 超過のものを担当者ごとに @メンション付きで投稿 | `#todo-アラート` |
| 毎週月曜 | 最終接触から14日以上・未クローズの求職者＝放置リスト | `#todo-アラート` |
| 毎週月曜 | 30日以上更新のない「募集中」求人＝鮮度切れリスト | `#todo-アラート` |
| 随時 | 面談実施済みで選考エントリーが0件の求職者＝**紹介漏れ** | `#todo-アラート` |
| 随時 | 必須項目の空欄を条件付き書式で赤表示 | シート上 |

最後の「面談したのに1社も推薦していない人」は、いまの構造では絶対に検知できません。ここが機械化できるのが最大の効果です。

## 7. Slack の運用ルール（4行）

1. **一次情報をSlack本文に書かない**。書いた瞬間に失われる情報だと考える。
2. 求職者・求人の話をするときは**必ずIDを書く**（`C-0042` `J-0015`）。自動投稿には常にIDが入るので、Slack検索が索引として機能する。
3. チャンネルを分ける：`#報告-面談` `#報告-企業` `#進捗-選考`（自動投稿専用）、`#相談`（議論）、`#todo-アラート`（自動リマインド）。
4. 議論は必ずスレッドで。親メッセージにIDがあれば経緯が全部そこに紐づく。

## 8. 技術的リスク：ファイルサイズ

現状のサイズは看過できません。

| ファイル | サイズ |
|---|---|
| ★面談・面接管理シート | 38.6MB |
| R8.7月　ハブワークス様　候補者リスト | 31.9MB |
| 開発エンジニア経験者　候補者リスト | 31.7MB |
| 株式会社Will様　候補者リスト | 31.2MB |
| 面談シート | 11.1MB |

Googleスプレッドシートには **1ファイル1,000万セル**の上限があり、その手前から実用的な限界（開くのが遅い、関数の再計算が止まる、共同編集が詰まる）が来ます。原因は2つ：

1. **月次でタブを複製している**（「面接数6月 のコピー」）→ 明細1枚＋期間フィルタにすれば不要
2. **面談情報の全文を1セルに入れている**（数千字の経歴・希望条件が1セル）→ 長文はGoogleドキュメントか別タブに逃がし、マスタには**リンクだけ**を持つ

この2つを直すだけでサイズは大幅に落ちます。**サイズ上限に当たってから直すのは非常に高コスト**なので、早めに手を打つべきです。

## 9. 進め方（優先順位順）

| 時期 | やること | 効果 |

| **今週（応急処置）** | ①旧「送客可能企業リスト」「求人管理簿」「新マトリックス」「【テスト】〜」を**閲覧専用にしてタイトル先頭に `【凍結】` を付ける**（`※使用禁止` 方式が既にあるので同じやり方でOK）。②「無題のスプレッドシート」2件を削除。③どれが正かを1行でSlackにピン留め | 「どっちが正？」が即日消える |

| **Week 2** | **選考進捗シートを新設**。`★面談・面接管理シート` の週次・月次を、そこからの自動集計に差し替え | 月次手入力が消える。漏れ検知の土台 |

**この順番を崩さないこと。** 統合前に自動化に着手すると、統合されていないシートを自動化してしまい二度手間になります。

## 10. 将来の選択肢と判断基準

以下に該当したら専用ツール（人材紹介向けATS / kintone）を検討：

- 同時に動く選考エントリーが常時50件超（★現状の週次数値を見る限り、既に近い水準）
- マスタを編集するメンバーが5〜6名超（★CAが佐藤・竹林・別府・寺本・松永・畠山・福岡・今井と8名確認できるため、**既に該当**）
- 変更履歴を追う必要が出た

現時点でも規模的にはATS検討圏内です。ただし**移行前に本ドキュメントの整理（特に選考進捗の明細化）をやっておかないと、ツールを入れても同じ問題が再発します**。逆に整理さえできていれば、移行は単なるデータ投入になります。

## 11. 確認が必要なこと
